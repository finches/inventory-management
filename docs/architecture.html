Filter Data Flow

How the four global filters (Time Period, Warehouse, Category, Order Status) move from UI to data and back

1
FilterBar.vue
Four <select> elements bind via v-model to shared refs in the useFilters() composable, so every view reacts to the same filter state instantly.
2
View component
Each view calls getCurrentFilters() to build { warehouse, category, status, month } and re-fetches on change via watch/onMounted.
3
api.js
Converts the filters object into a query string with URLSearchParams, dropping any 'all'/falsy values, and calls axios.get('http://localhost:8001/api/...').
4
FastAPI query params
Endpoints declare Optional[str] = None params that FastAPI parses automatically from the query string.
5
In-memory filtering
apply_filters() narrows the in-memory list by warehouse/category/status; filter_by_month() additionally matches exact months or quarter codes against order_date.
6
Pydantic validation
Endpoints with a response_model validate and serialize the filtered results to JSON before returning them.
7
Vue computed properties
The response is assigned to a ref (e.g. orders.value); template-facing computed properties derive charts, KPIs, and tables reactively from it.

Notable Findings

Frontend/backend mismatch api.js defines getTasks/createTask/deleteTask/toggleTask and createPurchaseOrder/getPurchaseOrderByBacklogItem, calling /api/tasks and /api/purchase-orders — but no such routes exist in main.py. These calls 404 against the real backend; the UI degrades silently via try/catch.
Orphaned view views/Backlog.vue exists and fetches backlog + inventory data, but is not registered in the router (main.js only wires up Dashboard, Inventory, Orders, Demand, Spending, Reports).
Unused models PurchaseOrder and CreatePurchaseOrderRequest Pydantic models are defined but no route uses them; purchase_orders.json is only consulted to compute the has_purchase_order flag on backlog items.
